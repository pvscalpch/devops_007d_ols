Repositorio del microservicio ms-auth-user del proyecto CarMeet, desarrollado por Cristian Bravo y Pascal Pacheco para la asignatura Ingeniería DevOps (DOY0101). El microservicio se usa como base para implementar un flujo de trabajo DevOps con Git, GitHub y GitHub Actions. Está construido con Java 17, Spring Boot, Maven, MySQL, Flyway y GitHub Actions.

Antes de definir la estrategia del equipo se compararon tres modelos de ramificación. GitFlow trabaja con las ramas main, develop, feature y hotfix, y conviene en proyectos con versiones formales y varias personas trabajando en paralelo, porque separa el código estable del que está en desarrollo; su costo es que las ramas viven mucho tiempo y los merges se vuelven pesados si se despliega muy seguido. GitHub Flow usa solo main más ramas cortas de funcionalidad, y encaja cuando cada Pull Request aprobado se despliega de inmediato a producción, pero no contempla varias versiones vivas a la vez ni entornos de QA separados. Trunk-Based Development trabaja sobre una sola rama principal con ramas que duran horas, y sirve en equipos con integración continua madura y feature flags que entregan varias veces al día, aunque exige una automatización de pruebas sólida y resulta riesgoso en equipos que recién comienzan.

Para este proyecto se adoptó GitFlow. La rama main contiene la versión estable, develop es la rama de integración de los cambios, las ramas feature se usan para nuevas funcionalidades y las ramas hotfix para correcciones urgentes. El flujo definido es feature hacia develop y develop hacia main; las correcciones urgentes nacen de main, se integran a main y se propagan de vuelta a develop para que la corrección no se pierda. Los cambios que llegan a main deben estar previamente revisados y validados mediante Pull Request.

Sobre las convenciones de trabajo del equipo. Las ramas se nombran con el prefijo feature, hotfix o docs seguido de una descripción breve en minúsculas, sin tildes ni espacios, describiendo qué se hace y no quién lo hace; la rama se elimina una vez integrada. Los mensajes de commit siguen la convención Conventional Commits, con el formato tipo seguido de dos puntos y una descripción en imperativo, usando feat para funcionalidades nuevas, fix para correcciones, docs para documentación, ci para el pipeline, test para pruebas y chore para mantenimiento; un ejemplo real de este repositorio es "feat(auth): exponer endpoint publico de health check". La estructura de carpetas separa el pipeline en .github/workflows, el código fuente en src/main/java organizado por responsabilidad en config, controller, dto, model, repository, security y service, las migraciones de base de datos en src/main/resources/db/migration, y las pruebas en src/test/java replicando el mismo árbol del código fuente para que la ubicación de un test sea predecible. En cuanto al control de versiones, las versiones estables de main se marcan con tags anotados siguiendo versionado semántico, las migraciones de Flyway se versionan y no se modifican una vez aplicadas, y ningún valor sensible se guarda en el repositorio: los secretos se inyectan como variables de entorno desde GitHub Actions Secrets. La estrategia de revisión establece que nada entra a main ni a develop sin Pull Request, que cada Pull Request requiere la aprobación del otro integrante y que el pipeline debe estar en verde antes de integrar.

El trabajo colaborativo se realizó con los comandos clone, config, switch, add, commit, push, pull, merge, tag y log. Se abrieron cinco Pull Requests: el primero incorporó el pipeline de integración continua desde la rama feature/ci-pipeline, el segundo agregó un endpoint público de health check desde feature/health-endpoint, el tercero incorporó esta documentación desde docs/readme-completo hacia develop, el cuarto integró develop hacia main como release v1.0.0 y el quinto corrigió el manejo del secreto JWT desde hotfix/jwt-secret-env.

Cabe señalar que los Pull Requests primero y segundo se integraron directamente a main sin pasar por develop, en contra del flujo declarado. La causa fue que GitHub propone como rama base la rama por defecto del repositorio, que en ese momento era main, y la sugerencia se aceptó sin revisarla. La desviación se detectó al inspeccionar el grafo del historial con git log --all --graph --decorate, y se corrigió sincronizando develop con main mediante un merge explícito y cambiando la rama por defecto del repositorio a develop, de modo que los Pull Requests siguientes propusieran la base correcta. La trazabilidad completa del historial se encuentra en el archivo docs/trazabilidad.txt.

El pipeline de integración continua está definido en .github/workflows/ci.yml y se ejecuta con cada push a develop y con cada Pull Request hacia main, además de poder lanzarse manualmente para probar una rama antes de abrir el Pull Request. Levanta un contenedor MySQL como entorno cloud simulado, descarga el código, instala el JDK 17 con caché de dependencias de Maven, compila el proyecto, aplica las migraciones de Flyway, ejecuta las pruebas con mvnw verify y publica el archivo .jar resultante como artefacto descargable, terminando con un resumen de la rama, el commit y el estado final de la ejecución.

Para ejecutar el microservicio de forma local se requiere JDK 17 o superior y una instancia de MySQL en el puerto 3306. El comando es mvnw spring-boot:run y el servicio queda disponible en el puerto 8090, con un endpoint público de verificación en /api/health.
